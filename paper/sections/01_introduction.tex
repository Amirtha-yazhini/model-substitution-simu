\section{Introduction and Threat Model}\label{sec:intro}
Large language models are increasingly used through an intermediary such as an API
provider. A client pays for a certain model and gets the response along with the model's name,
but the name alone cannot show whether the provider substituted another model~\cite{cai2025}.
Providers have several reasons to substitute, and the money involved is large. For the token mix used in this paper the substitute costs 11.5\% of the genuine
model, which means that a gateway that swaps one request in ten saves about \$88 per \$1,000 of
billed traffic.

So far attestation with trusted hardware~\cite{cai2025} is the only definite way to check
this, and gateways do not offer it today. What a
client can do is check the responses using black box auditors. They send probe requests and use the
response text, timing and other metadata to check whether the advertised model actually answered.

These black-box auditors employ several statistical methods. From April 2025 onwards at least 7
such auditors have been proposed~\cite{cai2025,zhu2025rut,lin2026gatescope,fang2026kbf,bruckner2026,iris2026,difr2025}.
Each was tested on its own testbed against its own adversaries, with thresholds chosen on the
same data the results are reported on. A frozen-threshold replication~\cite{holdout2026} shows
how fragile this is in practice. A method with perfect accuracy during development fell to 50\%
sensitivity on fresh model-pairs and half of those pairs could not be scored at all. The proposed
auditing methods so far have never been compared on a common testbed against a common adversary,
and the papers that consider a gateway which can detect auditing~\cite{cai2025,zhu2025rut,iris2026}
test it only against their own probes.

\textbf{Threat model.} The user sends HTTPS requests to a gateway that seems to provide model $M$.
Routing and response metadata is under complete control of the gateway. For each request four
things may happen: the gateway may forward it to $M$, to a cheaper substitute $M'$, to another
provider of $M$ or to a cache. Apart from this, it may also rewrite the reported model name, the
\texttt{usage} token counts and \texttt{system\_fingerprint} and add
delay. It can also classify requests by their shape. Like a real
adversary, the gateway tries to save as much as possible while keeping the
probability of detection low. The clients get to see the response text, client-side latency, the
\texttt{usage} block, the fingerprint and the logprobs where the endpoint exposes them.
The client can measure timing itself; the other signal is the content. To test for
false positives, honest variation such as load balancing across legitimate providers of
$M$ is allowed.

\textbf{Contributions.}
\begin{itemize}
\item SHIM, a shared adversarial testbed: an OpenAI-compatible gateway with twelve
  adversary arms and a hidden ledger of the true answers. Arms such as probe-aware
  evasion and canary-awareness were studied before for single detectors~\cite{cai2025,iris2026};
  here every arm runs against every detector.
\item A sealed comparison of six auditors. We reimplemented five published
  auditing methods and added an e-value fusion, and hashed and tagged all thresholds before
  evaluation. An auditor that cannot run on a specific arm reports as
  `uninformative'.
\item A deployability check. None of the 11 endpoints returns the logprobs our version of
  the rank-based auditor needs. The most recent one-token fingerprint method
  runs on only 4 of them, because many real models spend tokens on hidden reasoning.
\item Three negative results. Every auditor drops to chance against probe-aware
  evasion. False-positive budgets set a dilution floor of $\epsilon^* = 0.10$. Timing-based auditors
  cannot tell fraud from sanctioned routing.
\end{itemize}
